## Fixed product decisions

1. Cursor Bridge and Grok Build Supervisor remain independently installed,
   versioned, updated, tested, and released.
2. Existing Codex, Claude Code, Grok Build, and Pi installation/update commands
   must not be renamed or broken.
3. Users keep working in their existing client: Codex (**recommended**), Claude
   Code, or Pi. The plugins add Cursor and Grok Build coordination abilities;
   the repository is not presented as a separate orchestrator product.
4. Cursor CCE remains the first Cursor Bridge capability explained to users.
5. `cursor_do` becomes substantially more visible, while remaining optional,
   clearly bounded, and subject to primary-agent verification.
6. Public copy says **complete Cursor + Grok Build workflow**. It must not imply
   support for Grok Imagine, Grok web, Grok API, or concurrent host-client
   writers.
7. Windows remains the only end-to-end supported operating system until another
   platform passes its own live acceptance matrix.
8. English and Simplified Chinese documentation remain meaning-aligned and
   maintained.
9. Other languages are described as runtime-adaptive, never as fully translated
   or fully localized.

## Language architecture

### Canonical baseline

Hard machine/adapter semantics use canonical English:

- fallback error and guidance text;
- internal CCE and `cursor_do` scaffolds;
- direct stderr diagnostics that bypass a host model;
- semantic definitions carried by Skills.

Canonical English is an implementation baseline, not a forced user language.

### User-facing language precedence

1. An explicit language request in the current task.
2. The language of the user's most recent substantive message/current task.
3. A host/session or operating-system locale only when the host genuinely knows
   it and there is no conversational signal.
4. English as the final fallback.

Inferred language is task-local and is never persisted globally.

### Byte-stable machine contract

The following values are never translated:

- tool names and slash commands;
- JSON keys, states, enum values, and error/status codes;
- confirmation strings such as `OPEN_GROK_SESSION`;
- permission IDs, form field keys, and exact option values;
- paths, commands, hashes, task/session/agent IDs;
- `CCE_SEARCH_RESULT`, its field keys and enums, `NOT_FOUND`, and
  `path:line` anchors.

Permission/input explanations may be localized, but the exact returned options
must remain visible and unmodified.

### Host-as-localizer

No public MCP tool receives a general `locale` parameter. The host agent
localizes semantic templates because it sees the current conversation.

Cursor and Grok task briefs use the current user language unless explicitly
overridden. A canonical English scaffold may wrap a brief, but it must request
that narrative output follow the query/task language.

Cross-host handoff does not silently translate a stored result artifact. The
current host explains or summarizes it in the current task language while
preserving the original artifact.

### Intent matchers

Existing English/Chinese intent matchers remain in this release. Other
languages fail open without blocking the underlying tools. Structured states
and explicit tool routing remain the preferred compatibility surface.

## Semantic user-message contract

Skills communicate these meanings in the current user language:

| State | Required meaning | Stable values to preserve |
|---|---|---|
| connecting | Startup is in progress; no action is required yet. | — |
| ready | Executor mode is active for this workspace; the terminal is ready; the user can state a task. | — |
| needs workspace trust | Grok waits for the user's decision in the visible terminal; do not rerun activation; Supervisor never decides for the user. | `/grok_execute on` |
| awaiting registration | The terminal is open and still starting; ask the user to check it; do not call it a confirmed trust screen. | — |
| needs permission | Explain the request and present exact options verbatim. | permission IDs/options |
| needs input | Relay the question; answer only from verified in-scope context. | form keys |
| completed | Report the claimed result/artifact and state that host verification remains. | paths, hashes, IDs |
| failed | Report one actionable cause and next step without dumping diagnostics. | error/status codes |
| Cursor recovery | Explain the blocker, retained binding, and one safe recovery action. | `needsAction`, `CURSOR_EXE`, ports |
| CCE result | Present evidence, gaps, coverage, and confidence in the query language. | result marker, keys/enums, anchors |
| `cursor_do` result | Report work, changed files, checks, and residual risk; primary agent accepts or rejects. | task/agent IDs, paths |

## CCE and cursor_do scaffold rules

The CCE scaffold becomes canonical English and adds this invariant:

> Write the intent restatement, relevance/relationship notes, coverage rationale,
> and gap descriptions in the same language as the query. Keep
> `CCE_SEARCH_RESULT`, field keys, enum values, `NOT_FOUND`, `none`, and all
> `path:line` anchors exactly as specified.

The `cursor_do` wrapper becomes canonical English and adds this invariant:

> Produce the final report in the language of the task text unless the task
> explicitly requests another language. Keep file paths, commands, identifiers,
> and machine values exact.

Changing the CCE scaffold invalidated the previous prompt-level acceptance and
required a fresh current-Cursor live matrix before publishing 5.5.0. The final
matrix used Cursor 3.17.19 after it replaced 3.17.8 on the acceptance machine.

### Prohibited claims

- Grok full family/full stack/全家桶 if it implies Imagine, web, or API coverage;
- support for all languages or full localization;
- unrestricted/autonomous `cursor_do` execution;
- concurrent multi-client writing;
- sandbox/isolation guarantees for prompt or path boundaries;
- macOS/Linux support before live acceptance;
- translating the Cursor product name;
- headline-level ACP/CDP/process/socket/permission internals.

## Ordered implementation blocks

Each block must be separately reviewable and revertible before publication.

### Block 0 — Supervisor 0.3.6 release hygiene

- Move current Supervisor `[Unreleased]` items into a dated `[0.3.6]` section.
- Verify every 0.3.6 manifest already agrees.
- Create component tag `grok-build-supervisor--v0.3.6`.
- Publish combined Release
  `Cursor Bridge 5.4.2 + Grok Build Supervisor 0.3.6 (New)`.

- Update only tests that intentionally pin the converted machine text.
- Leave comments, bilingual matchers, fixtures, and Chinese docs unchanged.

- Rewrite the scaffolds using the rules above.
- Keep normalizer markers/keys/enums byte-stable.

  compatibility or release claims.

### Block 3 — Host Skill language contracts

- Replace localized sentences with semantic templates and rendering rules.

### Block 6 — README positioning and release documentation

- Fix Pi omissions in the supported-host line and architecture diagram.

### Block 7 — Cursor Bridge 5.5.0 synchronization and build

  compatibility, changelog, and test version fields.
- Rebuild dependency-free Cursor runtime bundles.
- Build both Pi staging packages from final source.

### Block 8 — Acceptance, publication, and rollback boundary

1. Run unit/contract suites after each implementation block.
2. Complete the live matrix below.
3. Fetch and inspect remote divergence.
4. Commit and push source only after acceptance.
5. Tag `cursor-bridge--v5.5.0` and
   `grok-build-supervisor--v0.3.7`.
6. Publish one combined GitHub Release:
   `Cursor Bridge 5.5.0 (New) + Grok Build Supervisor 0.3.7 (New)`.
7. Publish immutable Pi packages last, after confirming their tarballs embed the
   tagged runtime versions.

Before tags/npm publication, rollback is a normal revert/fix-forward. After npm
publication, package versions are burned and recovery must roll forward.

## Completion definition

The work is complete only when:

- all implementation blocks are committed in reviewable order;
- all unit and live acceptance gates pass;
- source, dist, plugin caches used for acceptance, staged Pi tarballs, tags,
  releases, and registry packages report the intended versions;
- the bilingual README claims do not exceed the verified evidence;
- the repository is clean and local/remote commit IDs match.
